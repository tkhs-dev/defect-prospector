> 出典PDF: `cheng_rug.pdf`（元ファイルはリポジトリ外 `C:\Users\daiki\claude-tmp\rug\` に配置。
> パスワード保護されておりこのリポジトリには含めていない）。本ファイルは [doc/test-generation.md](test-generation.md)
> のRust向け拡張検討（[rug-integration-note.md](rug-integration-note.md) 参照）のために作成した要約。

- **著者**: Xiang Cheng, Fan Sang, Yizhuo Zhai, Xiaokuan Zhang, Taesoo Kim
- **所属**: Georgia Institute of Technology, George Mason University
- **対象**: Rust プロジェクト向けのユニットテスト自動生成（LLM＋静的解析＋ファジング）

---

## 1. 概要（一言で）

LLM に「このコードのユニットテストを書いて」と一度に頼むと、Rust では厳しいコンパイルチェック（型・トレイト境界・所有権など）に通らないコードが大量に出る。また通ったとしてもカバレッジが低い。
RUG は、

1. **型依存グラフに基づくボトムアップ型のコンテキスト構築**でコンパイル可能なテストを作り、
2. **生成テストをファジングハーネスに変換してファジング**することでカバレッジを広げる

という 2 本柱で、人手テストに迫るカバレッジ（GPT-4 で **71.37%**、人手 **73.18%**）を達成した。

---

## 2. 背景と動機

- crates.io の上位 30K クレートを調査したところ、**47.41% がテストカバレッジ 30% 未満**で、Rust のテスト不足は深刻。
- 既存手法の問題点:
  | 手法 | Rust での問題 |
  |---|---|
  | SBST（探索ベース, 例: RustyUnit） | 変異演算子が型・所有権・ライフタイムの正しさを保証できない。既存コードを親として変異させるため、使用頻度の低い関数に弱い |
  | ファジング（RULF, RPG） | ハーネスが必要。API 呼び出し列の探索空間が巨大。生成コーパスが大量で可読性も低い |
  | LLM（ChatUniTest 等） | Java でも 57.9% がコンパイルエラー。Rust ではさらに厳しい。分岐条件を推論できずカバレッジが伸びない |

### 動機付け例（bincode の `encode`）

```rust
fn encode<E: Encoder>(&self /* char */, encoder: E) -> Result<EncodeError>
impl<W: Writer, C: Config> Encoder for EncoderImpl
impl Writer for SliceWriter / IoWriter
impl<T> Config for T where T: R1 + R2 + R3   // プロキシ定義
pub struct Configuration<R1, R2, R3>
```

`E: Encoder` の具体型を作るには `EncoderImpl` → `Writer` / `Config` を解決する必要があり、さらに `Config` は「R1+R2+R3 を満たす任意の T」というプロキシ定義しかないため、コードベース全体から `Configuration` を探し当てる必要がある。関連ソース・rustdoc・サンプルを全部プロンプトに入れても、GPT-3.5/4 は正しいテストを書けなかった。

## 3. 課題の整理

### A. コンパイルチェックを通す難しさ
- **トレイトとトレイト境界**: ジェネリクスに入れる具体型の推論が難しい。合成・プロキシ定義があるとさらに困難。データ定義と実装が分離していることも LLM を混乱させる。
- **定義パス**: 型・関数・トレイト（例: `Encode` トレイト）を明示的に `use` しないとコンパイルできない。
- **連鎖エラー（cascading errors）**: 入力準備 → 関数呼び出し → アサーション、と長い推論チェーンのどこか一つでも誤れば失敗する。

### B. 低カバレッジ
- LLM はプログラムの実行状態を観測できないため、分岐条件を満たす入力を作れない。
- 実行パスを推論できないので、アサーションの期待値（オラクル）も誤りやすい。

## 4. 手法（RUG の設計）

全体フロー:

```
Rust プロジェクト
   │
   ▼ (§IV.A.1) 型依存グラフ構築（静的解析）
   ▼ (§IV.A.2) ボトムアップのコンテキスト構築（LLM + コンパイラ検証）
   ▼ ユニットテストコード
   ▼ (§IV.B.1) ファジングハーネス変換
   ▼ (§IV.B.2) ファジング → コーパスのフィルタリング・選択
   ▼ 最終ユニットテスト
```

### 4.1 型依存グラフの構築

有向グラフ `G = (V, E)`:

- **ノードの種類**
  - `v_trait`: トレイト境界制約を持つノード（例: `Writer`, `Config`）
  - `v_instance`: struct / enum など具体型（例: `EncoderImpl`, `IoWriter`）
  - `v_proxy`: プロキシ定義（`impl<T> Config for T where T: R1+R2+R3`）を表す特殊ノード
- **エッジ**: 始点が終点に依存することを表す（例: `EncoderImpl → Writer`）
- **葉ノード** = 具体型を持つノード

対象関数の各引数 `p_i` について、`p_i` から始まりプリミティブ型で終わる部分グラフ `g` がテストコンテキストの範囲となる。

> RULF/RPG の API 依存グラフと違い、**関数ノードを持たない型だけのグラフ**にすることで探索空間を大幅に削減し、関数呼び出し順序の決定は LLM に任せている。

### 4.2 ボトムアップ・コード生成（中核のアイデア）

既存の LLM 手法は「全コンテキストを渡して一発生成 → エラーなら修正」という **one-shot 方式**。RUG は問題を**依存グラフのノード単位のサブ問題**に分割し、**葉から根へ順に**解く。

- あるノードは、依存先がすべて解決済みになったら解決可能になる。
- 各ノードについて **Prompt 1**（「`{var-type}` 型の変数 `{var-name}` をコンストラクタ等で初期化するサンプルコードを埋めて。依存型 `{dependent-type}` は前ラウンドのこのコードを再利用して」）で LLM にコードを生成させる。
- 生成コードは **オラクルコンパイラ**でコンパイル可能か検証し、通ったものだけを次の親ノードに渡す（**検証済みの部分解をキャッシュ・再利用**）。
- 全引数が揃ったら **Prompt 2**（対象関数・定義パス・各引数の構築コードを渡してテストを組み立てる）で最終テストを生成し、再度コンパイラで検証。

ノード種別ごとの扱い:

| ノード | 処理 |
|---|---|
| Instance | 正しい定義パスを解決し、構造体定義・対象関数定義・トレイト定義・フィールド型・impl 関係を再帰的に収集してプロンプトに入れる |
| Trait | 境界制約の**積集合**を問い合わせて候補型を列挙。候補がなければトレイトの説明を与えて LLM に実装させる |
| Proxy | コンパイルコンテキスト内でプロキシ定義を適用して候補型を探す |

**Algorithm 1（BUILD_CONTEXT）** の要点:

1. `t` の依存先 `S` を取得し、未解決なら再帰的に `build_context`。
2. `t` が Instance なら、依存先の解 `D` を使って LLM に生成依頼 → コンパイル検証。失敗したら自然言語の説明（`descriptionGen`）で代替。
3. Trait/Proxy なら候補集合を使い、空なら LLM に実装させる。

**コーナーケース**:
- 型依存の**循環**: ランダムに順序を決めてサイクルを切り、該当サンプルコードをプロンプトから除く。
- **候補が複数**（約 17.48% のノード）: デフォルトは**ローカルクレート内の候補を優先**（LS 戦略）。
- LLM が 3 回試しても正解できない場合: サブタスクを未完了としてマークし、自然言語の説明をヒントにして次へ進む。

### 4.3 ファジングによる入力探索

#### (1) ファジングハーネス変換
- テストコード中の**プリミティブ値を抽出**し、ファザー入力バイト列から構築するローカル変数に置き換える（テスト本体の意味は保持）。
- 元のテスト値は**初期コーパス（シード）**として保存 → LLM が用意したサンプルデータがそのままファジングの種になる。
- 入力が変わるとアサーションが成り立たなくなるため、ファジング中は**アサーションを一時的に無効化**。ファジング後に結果を見てアサーションの期待値を置き換える。
- 実装には `rustc` + `syn` クレート、ファジングには **bolero + libFuzzer** を使用。

#### (2) コーパスの選択（Algorithm 2）
ファジングは数秒で数百のコーパスを生むため、後処理で絞り込む。
1. ファザーのビットマップではなく **ソースコードカバレッジ**で冗長な入力を除去。
2. **パス重み付きランキング**: 各コード領域に重み 1 を与え、その領域を通る n 個のコーパスで等分（各 1/n）。各コーパスのスコア = 通過領域の 1/n の合計。→ **ユニークな領域を多く通るコーパスを高く評価**し、閾値に従って選択。

## 5. 実装

- Rust toolchain **nightly-2022-12-10** 向け（他バージョン対応は MIR の変更への追従が必要）。
- 静的解析は **rustc コンパイラプラグインとして MIR** 上で動作。関連する型定義・内部型・関連トレイトの実装型・関数定義・rustdoc を再帰収集（対象クレート外の型に到達したら探索停止）。
- 本体は Python。LLM は `gpt-3.5-turbo-16k-0613` / `gpt-4-1106`。presence penalty = -1（与えたコンテキストを再利用させるため）、他はデフォルト。
- システムプロンプトで出力形式を指定し、常に「埋めるべきテンプレートコード」を与えて後処理しやすくしている。各質問の試行は最大 3 回。
- 生成結果の正しさはコンパイルとオラクルコンパイラプラグインによるローカル変数の型検出で確認。

## 6. 評価

研究課題: RQ1 従来ツールとの比較 / RQ2 LLM ベース手法との比較 / RQ3 アブレーション / RQ4 実用性 / RQ5 ロバスト性

### RQ1: 従来ツールとの比較

| 比較対象 | ベンチマーク | 既存ツール | RUG |
|---|---|---|---|
| RustyUnit（SBST, DynaMOSA） | RustyUnit の 7 クレート | 領域 34.70% | **54.84%** |
| SyRust（SAT ベースのプログラム合成） | SyRust の 2 カテゴリ | 領域 30.65% | **52.28%** |
| RULF / RPG（ファジング） | RULF の 13 クレート | 25.2% / 41.7% | **54.9%** |

- RUG のファジングは関数あたり 60 秒（RULF は 24 時間、RPG は 4 時間/ハーネス）。
- RUG が優位な理由: より多くの対象関数について呼び出しコンテキストを構築できる。RULF はジェネリクス未対応、RPG もスコープ外の候補を探せないケースがある。

### RQ2 / RQ3: LLM ベース手法との比較とアブレーション

- 対象: crates.io のダウンロード上位 **17 クレート**（平均 24,937 LoC；bincode, chrono, hashes, humantime, itoa, json, mio, nom, num-traits, demangle, crc32fast, ryu, semver, textwrap, time, toml, uuid）
- ベースライン: ChatUniTest（生成）＋ TestGen-LLM（コンパイラによるオラクル検査）＋ RustAssistant（エラー修正ループ）を Rust 向けに再実装して組み合わせたもの。

平均コード領域カバレッジ（Table II）:

| 設定 | GPT-3.5 | GPT-4 |
|---|---|---|
| Baseline（ファジングなし） | 40.79% (A) | 60.17% (E) |
| Baseline + ファジング | 45.41% (B) | 66.37% (F) |
| RUG ボトムアップのみ | 53.69% (C) | 65.11% (G) |
| **RUG（ボトムアップ + ファジング）** | **62.60% (D)** | **71.37% (H)** |
| 人手テスト（参考） | 73.18% (J) | |

- RUG 全体の向上: **+21.81%（GPT-3.5）/ +11.20%（GPT-4）**
- ボトムアップ構築の寄与: +12.90% / +4.94%（全体向上のおよそ半分）。ベースラインがテストを作れなかった API のうち **65.14%** を RUG がカバー。
- ファジングの寄与: +8.91% / +6.26%。高カバレッジ状態からでも約 6% 上乗せ。
- **GPT-3.5 + RUG（62.60%）が素の GPT-4（60.17%）を上回る**。

### RQ4: 実用性

- **カバレッジ**: GPT-4 版 RUG は 71.37% で人手の 73.18% に匹敵。17 クレート中 8 クレートで人手を上回り、hashes ではほぼ同等。chrono, nom, time などでは大幅に拡張。
- 人手に劣るケース（bincode, toml）: (de)serialization 用のテンプレートライブラリで実装型が少なく候補が見つからない。また構造化された入力が必要でファジングが効きにくい。
- **可読性・実利用**: 生成 248 件のうち **113 件を 12 プロジェクトに PR として提出**（テスト本体は無修正）→ **53 件マージ、17 件リジェクト、43 件レビュー待ち**。レビュー済みのうち約 75% がマージ。リジェクト理由は「対象関数が外部ライブラリからの再エクスポートでテスト不要」(16) と「長期放置でクローズ」(1)。
- **トークンコスト**: 型単位でキャッシュ・再利用するため、ベースラインの **51.3% のトークン**でカバレッジを 10.4% 向上（GPT-4 でのベースラインのコストは約 $1000）。

### RQ5: ロバスト性

- **学習データ漏洩の検証**: GPT-3.5（知識カットオフ 2021 年 9 月）に対し、2022 年 1 月以降に作られた 10 クレートで評価。ベースライン比 **+12.93%**。人手テストのある 6 クレートでは RUG 48.98% vs 人手 50.64%（差 1.66%）で、半数のクレートで人手を上回った。
- **候補選択戦略**: LS（ローカルクレート優先, デフォルト）、RR（ラウンドロビン）、UF（unsafe 領域が多い型を優先, RPG 風）を比較。LS がローカルのカバレッジを最も高めやすい（RR/UF は外部の型を選んでローカルのカバレッジが下がり得る）。

## 7. 関連研究との位置づけ

- **LLM × Rust**: RustAssistant（コンパイルエラー修正）、RustGen（自然言語→Rust コード）、Rust-Lancet（所有権違反の修正）は目的が異なる。
- **LLM × テスト生成**: CODAMOSA は SBST が行き詰まった時に LLM にシードを求めるが Python 向けで、型推論の課題を扱わない。
- **ファジング × LLM**: Fuzz4All 等はコンパイラのバグ発見が主目的で、生成コードのカバレッジ問題は扱わない。
- **RULF / RPG**: API 依存グラフ（関数ノードあり）を探索するのに対し、RUG は型のみのグラフ＋ LLM による呼び出し列決定で探索空間を削減し、初期コーパスも LLM から得る。

---

## 8. 限界

- 静的な型依存解析に依存するため、Java 等の強い型付け言語には移植可能だが、Python 等の弱い型付け言語では静的解析の精度に左右される。
- 特定の Rust ツールチェーンバージョンに依存。
- ファジング中にアサーションを無効化するため、その間のバグを見逃す可能性。
- コーパス選択でテスト数を制限すると一部カバレッジを失う可能性。
- 既存テストのフレームワークやコーディングスタイルを考慮していない（サンプルとしてプロンプトに与える改善余地あり）。

---

## 9. 所感・ポイント

- **核心は「LLM に大きな問題を一度に解かせず、型依存グラフで分割し、各ステップをコンパイラで検証してから積み上げる」こと**。これにより連鎖エラーを防ぎ、トークンも節約できる。
- LLM（文脈構築・可読なテスト・初期シード）とファジング（分岐条件を満たす入力探索）の**得意分野の相補的な組み合わせ**がうまく設計されている。
- 細かい点として、論文中で PR のマージ率が 75.14% / 75.71% と表記ゆれしている（53/(53+17) = 75.71%）。
